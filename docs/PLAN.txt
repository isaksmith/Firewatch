  NASA FIRMS Area API, free MAP_KEY

Hotspots (geostationary)

  Provisional data.

Historical hotspots (training)
  FIRMS yearly US country CSVs, no key, about 30 MB each. Example:
  https://firms.modaps.eosdis.nasa.gov/data/country/viirs-snpp/2023/viirs-snpp_2023_United_States.csv
  Download 2016-2024, filter to Kansas. Keep out of git.

Weather, live and historical
  Open-Meteo forecast and archive APIs, no key, 10k calls/day.
  Wind speed/direction/gusts, RH, temperature, precipitation, CAPE,
  weather codes. Same variables for training and live scoring.

Fire weather alerts (display only)
  NWS api.weather.gov/alerts, no key (User-Agent header required).

Lightning
  Proxy: Open-Meteo thunderstorm weather codes 95-99 and CAPE over the
  prior 24 h. Stretch: GOES GLM from NOAA's AWS open data bucket.

Terrain
  AWS Terrain Tiles (Terrarium PNG, elevation-tiles-prod), no key.
  Used for MapLibre 3D terrain and for slope in the spread model.

Infrastructure
  OpenStreetMap via Overpass: power=line (115 kV and up),
  power=substation, place=town/village/city. Pull once, cache as
  GeoJSON. (HIFLD Open shut down in 2025.)

Counties and regions
  US Census TIGER Kansas counties; EPA Level III ecoregions for the
  Flint Hills polygon.

Labels
  NIFC WFIGS Incident Locations (ArcGIS REST), no key.
  Verified: 891 Kansas incidents, 669 wildfire (WF) and 222 prescribed

========================================================================
5. ARCHITECTURE
========================================================================

Flow:
  FIRMS -> Ingest poller (every 5 min) -> Cluster into events
  -> Enrich (Open-Meteo, OSM layers, terrain) -> Score (model + rules)
  -> SQLite -> FastAPI -> React dashboard -> Alert detail -> 3D preview
  Spread simulator reads terrain and is called from the API.
  Operator actions go back through the API into SQLite.

Key design choice: alerts are per EVENT, not per pixel. Detections
within about 2 km and 12 h are grouped into one event. Multi-pass and
multi-satellite agreement becomes a confirmation feature.

Repo layout:
  backend/
    app/main.py              FastAPI app and routes
    app/config.py            env: FIRMS_MAP_KEY, MODE, BBOX, thresholds
    app/db.py                SQLite schema
    app/ingest/firms.py      poll FIRMS sources, dedupe
    app/ingest/weather.py    Open-Meteo current + archive
    app/ingest/nws.py        Red Flag Warnings
    app/features/cluster.py  detections -> events
    app/features/enrich.py   feature vector per event
    app/features/terrain.py  elevation and slope
    app/features/infra.py    distances to lines, substations, towns,
                             static heat sources
    app/scoring/rules.py     rules scorer and guardrails
    app/scoring/model.py     load model, predict, reasons
    app/sim/spread.py        arrival-time grid and isochrones
    data/                    cached GeoJSON, sample events, model files
  ml/
    build_dataset.py         FIRMS history + WFIGS labels + weather
    train.py                 train, calibrate, evaluate, export
    report.md                metrics and feature importance
  frontend/src/
    api.ts
    Dashboard.tsx            map + filters + ranked list
    AlertDetail.tsx          score, reasons, actions, history
    Spread3D.tsx             terrain, wind, animated spread, controls
  docs/PLAN.md, docs/DESIGN.md, docs/PLAN.txt

Database tables:
  detections     one satellite pixel per overpass (dedupe key:
                 source|lat4|lon4|acq_datetime)
  events         one fire; holds latest score, recommendation, status,
                 place label like "8 mi SW of Ashland, Clark Co."
  scores         score history per event with reasons
  actions        acknowledge / dismiss / escalate / reopen + note
  source_health  last good pull per data source

Alert status: new -> acknowledged | escalated | dismissed.
Auto-close after 24 h with no new detections. A dismissed event that
later rises to a higher recommendation reopens and is flagged.

API (base /api):
  GET  /alerts?min_score=&status=&since=&include_monitor=
  GET  /alerts/{id}            detections, features, reasons, weather,
                               nearby assets, actions, score history
  POST /alerts/{id}/actions    {action, operator, note}
  GET  /alerts/{id}/simulate?minutes=60&wind_kmh=&wind_from_deg=
  GET  /layers/{power_lines|substations|towns|static_sources|counties}
  GET  /health                 data age per source: ok / stale / down
  POST /ingest/run             manual poll
  POST /sample/replay          stream sample events in over ~60 s

MODE=sample feeds frozen fixtures through the same pipeline so the demo
never depends on a live overpass or venue Wi-Fi.


========================================================================
6. ML SCORER
========================================================================

What the score means:
  Not "is this pixel hot" (FIRMS already says that). Our score is the
  probability that this event is an uncontrolled wildfire worth a
  response, scaled 0-100.

  Static heat source (refinery, ethanol plant)   -> Monitor (suppressed)
  Prescribed / ag burn (calm April Flint Hills)   -> Monitor/Investigate
  Threatening wildfire (red-flag day, near town)  -> Escalate

Thresholds (configurable per district):
  Escalate >= 70, Investigate 40-69, Monitor < 40

Features per event:
  Detection:     max and total fire radiative power, brightness, share
                 of high-confidence pixels, pixel size, day/night,
                 local hour
  Confirmation:  number of detections, number of distinct satellites,
                 minutes active, FRP growth between passes
  Weather:       wind, gusts, direction, RH, temperature, rain in prior
                 72 h, grassland fire danger index
  Lightning:     thunderstorm codes in prior 24 h (proxy)
  Context:       day of year, Flint Hills flag, elevation, slope,
                 distance to transmission line, substation, town, and
                 known static heat source, number of other events
                 within 25 km in the prior 24 h
  Every feature has a fallback. Any fallback marks the event "degraded."

Grassland fire danger index (McArthur Mk 4, Noble et al. 1980):
  GFDI = 2 * exp(-23.6 + 5.01*ln(C) + 0.0281*T - 0.226*sqrt(RH)
                 + 0.633*sqrt(U))
  C = curing % (default 95 Nov-Apr), T = deg C, RH = %, U = km/h
  Verify constants against the source.

Labels:
  Wildfire (1):        event within about 3 km and -12 h/+48 h of a
                       WFIGS WF incident
  Prescribed burn (0): matched to a WFIGS RX incident
  Static source (0):   inside our static heat-source mask (grid cells
                       with detections on many separate days), plus
                       FIRMS type = 2
  Unmatched:           excluded (many Kansas rural fires never reach
                       IRWIN, so unmatched does not mean "no fire")
  If too few labels by Sat 10 am, add clearly labeled synthetic events
  and say so in the pitch.

Rules scorer v0 (Friday; permanent fallback). Start at 30, clip 0-100:
  +10  any high-confidence detection
  +12  max FRP >= 50 MW   (+6 if >= 10 MW)
  +14  seen by 3+ satellites   (+8 if 2)
  +8   FRP at least doubled between passes
  +20  GFDI >= 50   (+12 if 25-49, +5 if 12-24)
  +8   gusts >= 64 km/h (40 mph)
  +6   RH <= 20%
  +8   within 3 km of a town or 1 km of a transmission line
  -45  within 1 km of a known static heat source
  -20  in Flint Hills, March-April, and GFDI < 12
  -10  5+ other events nearby in 24 h and GFDI < 12
  -10  10 mm or more of rain in prior 72 h

Model v1 (Saturday morning):
  - XGBoost, shallow trees, class weights; logistic regression baseline
  - Calibrated probabilities; score = round(100 * p)
  - Temporal split: train through 2022, validate 2023, test 2024
  - Reasons: XGBoost per-prediction contributions (pred_contribs),
    converted to score points; top 3 shown per alert, e.g.
    "+18 gusts 45 mph, +12 RH 14%, -9 Flint Hills burn season"
  - Saved files: xgb-v1.json, features.json, metrics.json

Guardrails (applied after the model, shown in the UI when they fire):
  - Within 1 km of a town or 0.5 km of a line, and not a static
    source: never below Investigate
  - Within 0.5 km of a static source and FRP not growing: cap at Monitor
  - Weather missing: use rules scorer, mark degraded

Re-scoring: when a detection joins the event, and hourly while open.
Notify only when the recommendation goes UP.

Evaluation for the pitch:
  ROC-AUC, precision in the top 10 alerts per day, false-alarm reduction
  vs. alerting on every FIRMS pixel, feature importance chart.
  Also: for matched Kansas wildfires, first satellite detection time vs.
  reported discovery time. Report honestly either way.


========================================================================
7. 3D SPREAD PREVIEW
========================================================================

Purpose: "where could this go in the next 30-60 minutes." Labeled on
screen as a simplified grass-fire estimate, not an operational
prediction.

Fire behavior (all fuel treated as cured grass; verify constants):
  1. Dead fuel moisture:  MC = 9.58 - 0.205*T + 0.138*RH
  2. Moisture factor:     MC < 12:  phiM = exp(-0.108*MC)
                          MC >= 12: phiM = 0.684 - 0.0342*MC (U <= 10)
                                    phiM = 0.547 - 0.0228*MC (U > 10)
  3. Curing factor:       phiC = 1.12 / (1 + 59.2*exp(-0.124*(C - 50)))
  4. Head spread rate, km/h (CSIRO grassland, Cheney et al. 1998):
                          U < 5:  R = (0.054 + 0.269*U) * phiM * phiC
                          U >= 5: R = (1.4 + 0.838*(U-5)^0.844)
                                      * phiM * phiC
  5. Fire shape:          LB = 1.1 * U^0.464 (U >= 1), else 1
                          e = sqrt(1 - 1/LB^2)
                          R(theta) = R * (1 - e) / (1 - e*cos(theta))
                          theta = angle from downwind direction
  6. Slope:               multiply by exp(0.069 * s), s = slope in degrees
                          along travel direction, clamped to +/-20
                          (doubles per 10 deg upslope, halves downslope)

Grid and output:
  - 12 x 12 km around the event, shifted 3 km downwind, 60 m cells
    (200 x 200)
  - Fire arrival time per cell via Dijkstra over 16 neighbors
  - Isochrones every 5 min as GeoJSON polygons, up to 60 min
  - Impacts: first minute each town, line, and substation is reached
  - Target under 500 ms per call; cache by event + rounded wind
  - Tests: zero wind on flat ground is near-circular; more wind gives a
    longer head run; flipping wind mirrors the shape

Frontend view:
  - Satellite imagery on terrain (exaggeration 1.5), camera pitched 60
    degrees looking downwind
  - Isochrone rings draped on terrain, yellow (5 min) to dark red
    (60 min); bright line for the current front
  - Wind shown as drifting particles plus a big arrow at the ignition
  - Towns, lines, substations overlaid; an asset turns red when reached
  - Side panel: observed wind, override toggle, speed slider, direction
    dial, impacts list ("345 kV line 22 min, Ashland 38 min"), head
    spread rate, area at 60 min
  - Bottom bar: play, 0-60 min time scrubber, 1x/4x, reset to observed
  - Wind override re-calls /simulate (debounced 250 ms)

========================================================================
12. COST, STAND-UP, AND FAILURE (SLIDES THE RFP ASKS FOR)
========================================================================

Cost: all data is free and public. One small cloud VM, about $10-25 per
month, covers all 105 Kansas counties. A district needs only a browser:
no fiber, no sensors, no full-time operator.

Stand-up: about one day. Set the district boundary, load local assets
(towns, lines, critical facilities), set alert contacts, tune
thresholds against last season's events.

Failure behavior (fail visible, never silent):
  FIRMS down or delayed  -> banner with data age; GOES still gives
                            repeat looks; unscored hotspots still shown
  Weather API down       -> score with detection + context only; alert
                            marked "degraded confidence"
  Clouds / no overpass   -> shown as a coverage gap, not "no fire";
                            911 remains the primary path
  Poor field connectivity-> alerts are small text payloads (SMS/email
                            ready); dashboard is optional
  Model wrong            -> human always decides; guardrails near towns
                            and lines; actions logged for retraining

13. DEMO SCRIPT (UNDER 5 MINUTES)
========================================================================

1. Problem (30 s): Kansas grass fires; 911 calls come late; raw FIRMS
   on a spring day is dozens of dots, mostly prescribed burns.
2. Ingest (30 s): hit Replay; events stream onto the map.
3. Confirm (60 s): ranked list. Starbuck-like event scores ~91 with
   reasons; Flint Hills burn ~22; refinery ~5. Toggle "show suppressed."
4. Respond preview (90 s): open 3D; spread runs toward a town and a
   transmission line; change wind direction and watch it swing.
5. Act (30 s): escalate with a note; show the logged history.
6. Why trust it (60 s): evaluation numbers, feature importance, cost /
   stand-up / failure slide.

14. POSITIONS ON OPEN QUESTIONS
========================================================================

- Primary customer: Kansas rural fire district dispatch + Kansas Forest
  Service. Utilities served by the same alerts plus the asset overlay.
- Satellite latency and gaps: stated honestly. Polar satellites pass a

  911 calls; it does not replace them.
- Thin labels: temporal split, simple model, honest synthetic data,
  rules guardrails.
- Trusted thresholds: start at 70/40, show calibration, let each
  district tune, log every override.
- Human review: always. The system ranks and explains; people decide.
